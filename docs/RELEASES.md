# FormForge Releases & Branching Model

## Branching model (trunk-based)

- `main` is the single long-lived branch and is always deployable.
- Feature work lands via short-lived branches + pull requests into `main`.
- Every PR runs `CI` (typecheck, zero-warning lint, security suite) and the
  `Security scan` (CodeQL, `npm audit`, secret scan). PRs with failing checks
  are not merged.
- Weekly scheduled scans run on `main` even without code changes.
- Branches are deleted on merge: GitHub's `delete_branch_on_merge` handles the
  normal case and `.github/workflows/auto-delete-branch.yml` is the explicit
  cleanup pass for anything it misses. A merged PR never leaves a stale branch
  or a second open PR behind.

## Versioning

Semantic Versioning (`MAJOR.MINOR.PATCH`) derived from
[Conventional Commits](../CONTRIBUTING.md#-commit-messages-conventional-commits).

There is exactly **one** source of truth: `package.json` → `version`.

| Surface | How it gets the version |
| :--- | :--- |
| API (`/api/health`, `/api/openapi.json`) | `src/lib/version.ts` imports `package.json` |
| Dashboard footer | `NEXT_PUBLIC_APP_VERSION`, injected by `next.config.ts` at build time |
| `README.md`, `version.md` | updated by release-please (`x-release-please-version` markers) |
| Git tag / GitHub Release | created by release-please as `vX.Y.Z` |
| `docs/CHANGELOG.md` | generated by release-please from Conventional Commits |

Never edit a version by hand in more than one place. Bump it in the Release PR
(or let release-please do it) and every surface follows.

`docs/CHANGELOG.md` remains the authoritative release-notes file: the Release
workflow extracts the section matching the tag.

## Automated release (release-please)

Nothing is published without merging the Release PR. That merge **is** the
approval.

1. A Conventional Commit lands on `main` (`feat:`, `fix:`, `perf:`, …).
2. `.github/workflows/release-please.yml` runs and opens — or updates — a PR
   titled `chore(main): release X.Y.Z` on the branch
   `release-please--branches--main`.
3. That PR contains the version bump in `package.json` + `package-lock.json`,
   a new `## [X.Y.Z]` section in `docs/CHANGELOG.md`, and the matching version
   in `README.md` and `version.md`.
4. **Approval: merge the Release PR.** Review the generated changelog first —
   it is written from commit messages.
5. On merge, release-please creates the `vX.Y.Z` tag and the GitHub Release for
   the merged commit, then dispatches `release.yml` with that exact tag.
6. `release.yml` runs `validate-tag` (tag must equal `package.json`), the full
   `ci-gate` (typecheck, lint, security suite, Cloudflare build), then
   `create-release`: SPDX SBOM, Sigstore keyless signature, and the assets
   attached to the Release. `create-release` runs in the `release` environment,
   so a reviewer can be required before signing.

### Why required checks still run on the Release PR

A PR opened with the default `GITHUB_TOKEN` does **not** emit `pull_request`
events, so no workflow would start and the required checks would never report —
the Release PR could never merge. `release-please.yml` therefore dispatches
`ci.yml` and `security-scan.yml` on the release branch, which reports every
required check against its head commit.

The cleaner long-term setup is a `RELEASE_PLEASE_TOKEN` repository secret: a
fine-grained PAT with `contents: write` and `pull-requests: write`. The workflow
uses it automatically when present, and release-please's PRs then trigger normal
`pull_request` events.

```bash
gh secret set RELEASE_PLEASE_TOKEN   # paste the PAT when prompted
```

## Manual release (escape hatch)

```bash
# 1. Land the version bump + changelog section on main through a normal PR.
# 2. Then tag the merge commit:
git tag -a v1.2.0 -m "FormForge v1.2.0"
git push origin v1.2.0
```

The tag push runs the same `release.yml` pipeline (`validate-tag` → `ci-gate`
→ `create-release`), so the manual path cannot skip the gate.

## Release assets

Every release attaches `docs/CHANGELOG.md`, `CHANGELOG.md`,
`formforge-sbom.spdx.json` and its `formforge-sbom.spdx.json.bundle` Sigstore
signature. Verify the SBOM offline with:

```bash
cosign verify-blob ./formforge-sbom.spdx.json \
  --bundle ./formforge-sbom.spdx.json.bundle
```

## Rollback

```bash
git checkout v1.1.1
npm ci && npm run typecheck && npm run test:security
npm run deploy
```

Rolling back the Worker does not roll back D1. Migrations are additive and
idempotent (`src/db/auto-migrate.ts`), so an older release keeps working against
a newer schema; restore from a D1 export only if data itself is wrong (see
`docs/RUNBOOK.md`).

## Pre-release checklist

- [ ] The Release PR's changelog section is accurate and dated.
- [ ] `npm run typecheck`, `npm run lint`, `npm run test:security`,
      `npm run test:features` green locally.
- [ ] CI + security scan green on `main`.
- [ ] D1 backup exported (`docs/RUNBOOK.md` drill).
- [ ] Release PR merged; `vX.Y.Z` tag and GitHub Release exist.
- [ ] Release published with notes + SBOM + signature verified on GitHub.
- [ ] Release branch deleted, no open PRs or stale branches left behind.
